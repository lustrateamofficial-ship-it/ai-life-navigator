# AI Life Navigator 🧭

Персональный AI-навигатор жизни: Telegram Bot + Telegram Mini App.
Отвечает на вопросы «Где я?», «Куда я иду?», «Что делать сейчас?», «Почему я остановился?».

Это **полный кодовый каркас** по мастер-ТЗ (раздел 51), готовый к тому, чтобы вписать
ключи и задеплоить. Все 11 этапов представлены кодом; часть — в виде готового MVP,

## Технологии

- **Backend**: Node.js + TypeScript + Express + Prisma + PostgreSQL
- **Frontend**: React + TypeScript + Vite + Zustand + Telegram Mini Apps SDK
- **AI**: провайдер-агностичный слой (`backend/src/services/ai`), подключен Anthropic
- **Bot**: node-telegram-bot-api
- **Security**: helmet, express-rate-limit, HMAC-проверка Telegram initData, user_id isolation на каждом запросе
- **Tests**: vitest — юнит-тесты для Pearson correlation, linear regression, drift detection
- **Deploy**: Docker + docker-compose (миграции применяются автоматически при старте контейнера)

## Уникальные функции продукта (раздел 52 ТЗ)

- 🧭 **Direction Score** — взвешенная метрика 0-100, считается кодом на реальных данных (цели, здоровье, финансы, привычки, время)
- 🚨 **Drift Detection** — обнаружение, когда активность перестаёт быть связана с главной целью (с защитой от выводов на малой выборке)
- 🔍 **Correlation Engine** — настоящий коэффициент корреляции Пирсона между ежедневными метриками (привычки/задачи/вес/расходы), с порогом минимум 5 наблюдений и формулировками без причинности
- 🔮 **Future Simulation** — линейная регрессия по истории Direction Score + AI-объяснение с обязательным дисклеймером
- 🧠 **Personal Memory** — структурированная память, доступная пользователю ("что ты знаешь обо мне?")
- 📓 **Дневник** — свободные записи мыслей; AI извлекает из них устойчивые личные принципы
  (`MemoryItem.type = "principle"`) и держит их во ВСЕХ дальнейших AI-ответах (не только по
  запросу) — экран `/journal`, backend `routes/journal.ts` + `orchestrator.extractPrinciplesFromJournal`
- ⚡ **Next Best Action** — с fallback-режимом, если AI недоступен

## Быстрый старт

**Вариант 1 — весь стек в Docker** (то же самое, что в инструкции по деплою на Oracle):

```bash
cp .env.example .env
# впишите TELEGRAM_BOT_TOKEN, ANTHROPIC_API_KEY — DATABASE_URL трогать не нужно

docker compose up -d
```

Backend сам применит схему к базе при старте (`prisma db push` — см. примечание в
`docker-compose.yml` про то, почему не `migrate deploy`).

Оба образа (`backend`, `frontend`) — production-сборки в два этапа (см.
`backend/Dockerfile`, `frontend/Dockerfile`): в контейнере нет исходников и
dev-зависимостей, только скомпилированный код. Если вы поменяли код ПОСЛЕ первого
`docker compose up -d`, применить изменения автоматически не получится — нужно
пересобрать нужный сервис:

```bash
docker compose up -d --build backend   # после изменений в backend/
docker compose up -d --build frontend  # после изменений в frontend/ ИЛИ VITE_API_URL в .env
```

**Вариант 2 — backend/frontend напрямую на машине, Postgres в Docker** (быстрее для
разработки — не нужно пересобирать образ на каждое изменение):

```bash
cp .env.example .env
# впишите ключи, И поменяйте в DATABASE_URL хост "db" на "localhost" (см. комментарий
# в .env.example — порт 5432 проброшен наружу только на 127.0.0.1)

docker compose up -d db
cd backend && npm install && npx prisma db push && npm run dev
cd ../frontend && npm install && npm run dev
```

## Тесты

```bash
cd backend
npm install
npm test
```

Покрыты: Pearson correlation (`correlationEngine.ts`), линейная регрессия для Future Simulation
(`futureSimulation.ts`), логика Drift Detection (`driftDetection.ts`), пересчёт прогресса цели
(`goalProgress.ts`), стрик привычек (`habitStreak.ts`), переход на следующее срабатывание
повторяющегося напоминания (`reminderRecurrence.ts`), расчёт "сегодня" по часовому поясу
пользователя (`userTime.ts`), валидация формы файла при восстановлении из бэкапа
(`accountRestore.ts`) — везде, где неправильная математика или edge-case тише всего
проявляется, но дороже всего стоит.

Все тесты — чистые функции, без обращения к реальной базе данных (для этого там, где
расчёт раньше был перемешан с Prisma-запросами, арифметика вынесена в отдельную функцию —
тот же приём, что раньше применялся для `evaluateDrift`). Из-за этого один сценарий
принципиально не покрыт юнит-тестом: round-trip "экспортировал → восстановил →
данные совпадают" для `accountRestore.ts` требует реальной базы (вся функция обёрнута в
`prisma.$transaction`) — это честно отмечено в самом тестовом файле, а не забыто молча.

**CI** (`.github/workflows/ci.yml`, GitHub Actions): на каждый push/PR в `main` —
`prisma generate`, проверка типов (`tsc --noEmit`), юнит-тесты и сборка для backend;
проверка типов и production-сборка (`tsc && vite build`) для frontend. Не поднимает
Postgres и не требует реальных AI/Telegram-ключей — проверяет только то, что код
компилируется и тесты проходят, не полноценный Definition of Done (раздел 50 ТЗ),
который по-прежнему прогоняется вручную.

## Что нужно сделать вам

1. Поднять PostgreSQL (docker-compose уже настроен) и прогнать миграции.
2. Создать Telegram-бота через @BotFather, получить токен, настроить Web App URL.
3. Получить AI API ключ (Anthropic) и вписать в `.env`.
4. Задеплоить backend (Fly.io / Railway / VPS) и frontend (Vercel / статика за Nginx).
5. Прогнать сценарий Definition of Done (раздел 50 ТЗ) вручную.

Три пункта ниже физически нельзя сделать из окружения, где пишется этот код (нет
доступа ни в npm-реестр, ни в вашу консоль облачного провайдера) — их нужно сделать
руками один раз, на вашей стороне:

6. **Закоммитить `package-lock.json`** — на машине с доступом в интернет: `cd backend
   && npm install`, `cd ../frontend && npm install`, закоммитить оба получившихся
   `package-lock.json`. После этого в `.github/workflows/ci.yml` можно заменить
   `npm install` на `npm ci` — полностью детерминированные сборки плюс кэш
   зависимостей в CI.
7. **Снапшот диска VM в Oracle Cloud** — Compute → Instance → Boot Volume →
   Backups → Create Boot Volume Backup (можно поставить по расписанию). Это защита
   на случай, если сама VM/диск выйдет из строя физически — отдельно от бэкапа в
   Google Drive (тот защищает данные приложения, а не инфраструктуру).
8. **Sentry** (мониторинг ошибок, см. раздел ниже) — завести проект на sentry.io,
   скопировать DSN в `SENTRY_DSN` в `.env` на сервере.

## Резервное копирование — Google Drive

До этого момента бэкапов не было вообще — все данные жили в одном Docker-томе PostgreSQL
на одной VM. Теперь раз в неделю (суббота, 04:00) приложение само сохраняет файл со всеми
данными пользователя в его собственный Google Drive, в папку "Навигатор Жизни — бэкапы"
(`jobs/scheduler.ts` → `services/googleDrive.ts`).

**Максимум подробностей при минимуме места** — два независимых механизма:
- Каждый бэкап содержит ВСЕ данные без исключений (та же логика, что в ручном экспорте),
  просто упакован компактным JSON + gzip (`services/accountExport.ts`) — обычно в 5–15 раз
  меньше, чем файл из кнопки "Скачать мои данные" в Настройках (та остаётся читаемой,
  с отступами, это для глаз человека, а не для архива).
- Хранится не бесконечная история, а последние `BACKUP_RETENTION_WEEKS` копий (по умолчанию
  12 — это три месяца; меняется одной константой в начале `jobs/scheduler.ts`), старые
  автоматически удаляются из папки на Google Drive после каждой новой загрузки.

**Настройка (один раз, на стороне разработчика):**

1. console.cloud.google.com → создать проект (или использовать существующий)
2. APIs & Services → Library → найти "Google Drive API" → Enable
3. APIs & Services → Credentials → Create Credentials → OAuth client ID → тип
   **Web application**
4. В "Authorized redirect URIs" добавить `https://ваш-домен/api/google/callback`
   (ровно так же, как в `GOOGLE_REDIRECT_URI` в `.env`)
5. Скопировать Client ID и Client Secret в `.env` (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`)
6. Пока проект в режиме "Testing" (не прошёл верификацию Google) — на экране согласия
   Google нужно явно добавить свой же Google-аккаunt в список тестовых пользователей
   (OAuth consent screen → Test users), иначе Google откажет в доступе

**Использование (на стороне каждого пользователя):** Настройки → "Подключить Google Drive" →
вход в свой Google-аккаунт в открывшемся системном браузере → разрешить доступ. Используется
ограниченный scope `drive.file` — приложение видит только файлы, которые само создало, не
весь диск целиком.

Без этих переменных в `.env` кнопка подключения в приложении просто покажет ошибку о том,
что Google Drive не настроен на сервере — остальная функциональность не страдает.

Это бэкап уровня **данных приложения** (переживает смену сервера), а не уровня **диска**
(переживает поломку конкретной VM без переноса). Для второго — отдельно, по желанию:
Oracle Cloud поддерживает автоматические снапшоты блочного тома в консоли (Compute →
Instance → Boot Volume → Backups), без программирования, но с небольшой платой за объём.

## Шестой раунд: production-сборки и полноценное восстановление из бэкапа

Два самых крупных пункта из "осознанно не делаю сейчас" пятого аудита (см. ниже) —
сделаны.

**Production Docker-сборки.** Раньше контейнеры backend/frontend были по сути
development-окружением, запущенным в проде: `tsx watch` и `vite --host` внутри
контейнеров, исходники подмонтированы с хоста bind-томами, devDependencies стояли
рядом с рабочим кодом. Это работало, но лишний вес образов, лишние зависимости в
проде и неявная зависимость деплоя от файлов на хосте — не то, что хочется на боевом
сервере. Теперь оба `Dockerfile` — многоэтапные:
- `backend`: этап `builder` компилирует TypeScript (`tsc`), этап `runner` содержит
  только `dist/`, production-зависимости (включая сам `prisma` — он переехал из
  `devDependencies`, потому что нужен в рантайме для `prisma db push` при каждом
  старте) и генерирует Prisma Client заново под целевую платформу.
- `frontend`: этап `builder` собирает статику через Vite, этап `runner` — обычный
  `nginx:alpine`, отдающий готовые файлы (`frontend/nginx.conf`, с SPA-фолбэком на
  `index.html` для клиентского роутера и кэшированием хэшированных ассетов на год).
- **Важный нюанс с переменными Vite**: `VITE_API_URL` встраивается в собранный JS ВО
  ВРЕМЯ СБОРКИ образа, а не читается в рантайме — поэтому он передаётся как
  build-time ARG через `docker-compose.yml`, и смена адреса backend'а после первого
  деплоя требует пересборки именно frontend-образа (`docker compose up -d --build
  frontend`), а не просто перезапуска контейнера. Подробно расписано в
  `.env.example` и README (раздел "Быстрый старт").
- `Caddyfile` обновлён: фронтенд теперь слушает порт 80 (nginx), а не 5173
  (dev-сервер Vite).

**Восстановление из бэкапа** (`POST /account/restore`) — раньше можно было только
выгрузить данные (кнопкой или еженедельно в Google Drive), но не загрузить их
обратно, то есть "резервная копия" была дорогой в один конец. Теперь в Настройках,
рядом с кнопкой экспорта, есть "Восстановить из файла":
- Файл читается и парсится на клиенте, целиком отправляется на `/account/restore`.
- Восстановление **добавляет** данные, а не затирает аккаунт: цели, задачи, привычки
  и т.д. создаются заново с новыми id (внутренние связи между ними — например,
  задача → её цель — переносятся через карту старый id → новый id). Исключение —
  данные, для которых в схеме и так действует ограничение "одна запись на дату"
  (вес, вечерний чек-ин, дневная сводка, еженедельный/месячный отчёт, снимок
  Direction Score): здесь более новое значение из файла **перезаписывает**
  существующее на ту же дату — иначе восстановление в уже используемый аккаунт было
  бы почти бесполезно.
- Вся операция — в одной транзакции: либо восстановилось полностью, либо (при любой
  ошибке) не изменилось ничего.
- Не восстанавливаются векторные представления памяти (embeddings) — они и не
  входят в экспорт: это пересчитываемые данные, а не исходные.
- Побочная находка при реализации: `express.json()` по умолчанию принимает тело
  запроса не больше 100kb — любой файл экспорта с реальной историей легко превышает
  это, и запрос на восстановление тихо падал бы с 413 ещё до маршрута. Поднято до
  25mb.
- Заодно обнаружилось и исправлено: экспорт не включал `dailySummaries` (кэш
  дневной сводки) — добавлена в список выгружаемых таблиц.

**Чего всё ещё нет** (на момент этого раунда): часть пунктов из таблицы
"функциональные пробелы UI" (редактирование событий календаря с проверкой
пересечений, редактирование напоминаний/идей/записей дневника, история привычек,
управление памятью). Фото еды и Apple Health — осознанно не делаются по вашей
просьбе; Apple Health также архитектурно недоступен из Telegram Mini App (веб-вью
не имеет доступа к HealthKit — это ограничение платформы, а не недоработка).

## Восьмой раунд: рекомендации "как разработчик" — безопасность, пробелы в UI, полировка

После седьмого раунда был прямо задан вопрос "что ещё порекомендуешь делать дальше,
если бы ты был разработчиком приложения" — ниже то, что было в ответе, и что из этого
реализовано.

**Мониторинг ошибок (Sentry)** — `config/sentry.ts`. Без `SENTRY_DSN` ошибки по-прежнему
видны только в логах контейнера; с ключом — `Sentry.captureException()` в Express
error-middleware, `unhandledRejection` и `uncaughtException` (с `Sentry.close()` перед
`process.exit`, чтобы событие о фатальном крэше действительно успело уйти по сети).
`tracesSampleRate: 0` осознанно — это мониторинг ошибок, а не полноценный APM/tracing,
который стоил бы заметно больше бесплатного тарифа.

**Систематический IDOR-аудит по всем 18 файлам роутов** (не точечно, как раньше, а
единым проходом) — хорошая новость: новых дыр не нашлось. Все найденные ранее в
отдельных аудитах (`tasks.ts`, `ideas.ts`, `calendar.ts`) остаются единственными, что
когда-либо были; остальные 15 файлов routes/ уже скопированы по одному и тому же
паттерну (`findFirst({ where: { id, userId } })` перед любым update/delete).

**Редактирование там, где раньше можно было только создать/удалить**:
- Дневник (`PUT /journal/:id`, новый эндпоинт) — осознанно НЕ перезапускает извлечение
  принципов при правке текста (см. комментарий в `routes/journal.ts`): иначе правка
  опечатки тихо стирала бы уже извлечённые принципы, которые могли попасть в контекст
  AI-разговоров и в Портрет по дневнику.
- Идеи, Память, Напоминания — backend для PUT уже существовал (сделан в одном из
  прошлых раундов), не хватало только UI; добавлен.
- Календарь — backend PUT тоже уже был; добавлен UI, и ОТДЕЛЬНО — проверка
  пересечения с другими событиями (раньше её не было вообще). Предупреждает, а не
  блокирует (DESIGN_PRINCIPLES.md: "прощающий, а не гиперзаботливый интерфейс") —
  пересекающиеся события не всегда ошибка.
- "Слияние" записей памяти отдельным сделано не было: на практике это и есть
  редактирование одной записи (объединить суть) + удаление другой, а не отдельный
  мультивыбор — то, что уже добавлено, полностью закрывает этот сценарий.

**Привычки**: история за 30 дней (сеткой точек, разворачивается по тапу на привычку) —
данные уже приходили с бэкенда (логи в `GET /habits`), новых запросов не потребовалось;
и кнопка удаления привычки (бэкенд `DELETE /habits/:id` существовал, в интерфейсе кнопки
не было вообще).

## Седьмой раунд: погода, CI и расширенные тесты

Три оставшихся пункта из списка выше.

**Погода в утреннем дайджесте** (`services/weather.ts`) — переменные `WEATHER_API_KEY`/
`WEATHER_DEFAULT_CITY` существовали в `.env.example` с самого начала, но ничего их не
читало. Реализовано через OpenWeatherMap (сырой REST-запрос, без SDK — та же логика, что
для Google Drive): если у пользователя указан город в профиле (экран "Я"), погода берётся
для него, иначе — `WEATHER_DEFAULT_CITY`. Без ключа строка с погодой просто не появляется
в дайджесте — остальное работает как обычно (`isWeatherConfigured()` + флаг
`weatherConfigured` в `/health`, по аналогии с `aiConfigured`/`botConfigured`).

**CI** (`.github/workflows/ci.yml`) — на каждый push/PR в `main`: для backend —
`prisma generate`, проверка типов, юнит-тесты, сборка; для frontend — проверка типов и
production-сборка. Пока на `npm install`, а не `npm ci` — в репозитории ещё нет
`package-lock.json` (он появится при первом реальном `npm install` с доступом в
интернет, которого нет в среде, где написан этот код; после коммита лок-файла стоит
переключить workflow на `npm ci` для полностью детерминированных сборок).

**Расширенный тестовый набор** — было 3 файла (Pearson correlation, линейная регрессия
Future Simulation, Drift Detection), стало 8. Добавлены юнит-тесты на: пересчёт прогресса
цели (`goalProgress.ts`), стрик привычек (`habitStreak.ts`), переход к следующему
срабатыванию повторяющегося напоминания (`reminderRecurrence.ts`), расчёт "сегодня" по
часовому поясу пользователя — включая переход через границу суток/года и откат на UTC
при неизвестном часовом поясе (`userTime.ts`), и валидацию формы файла при восстановлении
из бэкапа (`accountRestore.ts`). Там, где арифметика раньше была перемешана с
Prisma-запросами внутри одной функции (прогресс цели, стрик привычки), чистый расчёт
вынесен в отдельную функцию по тому же принципу, что уже применялся для
`evaluateDrift` — так его можно протестировать без поднятия базы данных.

**Честно не покрыто и почему**: round-trip тест "экспортировал → восстановил → данные
совпадают" для `accountRestore.ts` требует реальной базы (вся функция — одна
`prisma.$transaction`) — такой тест либо не запустится в окружении без Postgres, либо
будет мокать Prisma целиком, что проверяет мок, а не реальное поведение. Отмечено прямо
в тестовом файле, а не пропущено молча.

## БАГ (найден при повторном аудите): Gemini/Groq-only конфигурация была заблокирована

Смысл добавления Gemini и Groq — дать возможность пользоваться AI-функциями бесплатно,
вообще без платного Anthropic-ключа. Но при первой реализации `isAiConfigured()` (проверяет
только Anthropic) ошибочно использовался как общий гейт для функций роутера/специалиста
(чат, распознавание еды, извлечение принципов из дневника, классификация интента) — тех
самых, что должны уметь работать через Gemini/Groq. На практике это означало: человек,
настроивший ТОЛЬКО бесплатные `GEMINI_API_KEY`+`GROQ_API_KEY` без Anthropic — то есть
сделавший ровно то, ради чего эти провайдеры вообще добавлялись — получил бы отказ
("AI временно недоступен") на чате и похожих функциях, хотя технически они прекрасно
работали бы.

Исправлено: добавлена `isAnyAiConfigured()` (`config/env.ts`) — true, если настроен хотя бы
один из трёх провайдеров. Используется для гейтов роутера/специалиста. `isAiConfigured()`
(именно Anthropic) оставлен только там, где код действительно вызывает исключительно его —
verifier-слой: отчёты, "почему я остановился", портрет по дневнику. `GET /health` теперь
отдаёт оба флага отдельно (`aiConfigured` — любой провайдер, `verifierConfigured` — именно
Anthropic), вместо одного смешивающего эти два разных смысла булева.

Проверено end-to-end в песочнице: с фейковым `GEMINI_API_KEY` и БЕЗ Anthropic — `/ai/chat`
реально доходит до попытки вызова Gemini (с логом честного fallback на Groq при сбое),
а не падает на гейте сразу.

## Трёхслойная AI-система и Портрет по дневнику

**Слои** (`services/ai/textGeneration.ts`):
1. **Роутер** — классификация сообщения (`naturalLanguageRouter.ts`)
2. **Специалист** — обработка внутри сектора (еда, финансы, "что делать сейчас", чат)
3. **Проверяющий** — сверяет готовый ответ с реальными посчитанными данными ПЕРЕД показом

Слои [1]/[2] — частые дешёвые вызовы, идут через Gemini (основной) → Groq (фолбэк) →
Anthropic (последний резерв, если ни один из первых двух не настроен). Слой [3] — редкие
вызовы с высокой ценой ошибки (отчёты, "почему я остановился", прогнозы, портрет по
дневнику), всегда через Anthropic. Без `GEMINI_API_KEY`/`GROQ_API_KEY` всё работает как
раньше, целиком через Anthropic — просто без экономии на частых вызовах.

`verifyAgainstData()` — новая функция: берёт черновой ответ специалиста и реальные
посчитанные кодом факты, просит модель сверить одно с другим и поправить расхождения
перед показом пользователю. Подключена к `analyzePeriod`, `whyDidIStop`, `simulateFuture`
и `generateSelfPortrait` — везде, где AI формулирует вывод о данных, а не просто
классифицирует сообщение.

**Портрет по дневнику** (`/portrait`, `services/ai/selfPortrait.ts`) — анализ записей
дневника + миссии + целей + принципов в отражение: наблюдаемые паттерны (с опорой на
конкретный текст, не категоричные утверждения), заявленные принципы, совпадение целей
с тем, что человек сам считает важным, и тон, в котором AI должен с ним разговаривать
дальше (`advisorVoice` подмешивается в контекст всех AI-ответов через
`contextBuilder.ts`). Намеренно не называется "клоном" — это не психологическая
диагностика, явно избегает клинических терминов и категоричных утверждений там, где
записи дневника чего-то не подтверждают.

## QA-аудит: что было найдено и исправлено

Полный проход по кодовой базе на предмет багов — от критичных (ломают сценарий целиком)
до мелких (тихо портят данные). Каждый фикс отмечен в коде комментарием `БАГ (найден при аудите)`.

**Критичные (ломали основной сценарий или деплой):**
- `<input type="datetime-local">` в Calendar.tsx/Reminders.tsx отправлял на backend формат без
  секунд/таймзоны, а zod-валидация требовала строгий ISO 8601 — создание календарных событий
  и напоминаний было невозможно в принципе. Исправлено на фронтенде (`.toISOString()`).
- Vite 5 dev-сервер по умолчанию блокирует запросы с чужим `Host`-заголовком — именно так
  работает Caddy. Деплой на Oracle VM из инструкции выше без этого фикса не открылся бы
  (`vite.config.ts: allowedHosts: true`).
- `Goal.progress` нигде не обновлялся (оставался 0 навсегда) — не было даже эндпоинта
  отметить этап выполненным. Это тихо занижало Direction Score. Добавлены
  `services/goalProgress.ts`, `PUT /goals/:id/stages/:id`, UI для отметки этапов.
- Один упавший async-хендлер или cron-джоб на ОДНОГО пользователя мог уронить процесс
  целиком для всех (unhandled promise rejection в Node 15+). Добавлены `express-async-errors`,
  `process.on("unhandledRejection"/"uncaughtException")`, обёртка `forEachUserSafely` в scheduler.

**Безопасность:**
- IDOR в задачах и финансах: можно было привязать свою задачу к чужой цели/этапу или
  транзакцию к чужому счёту и увидеть чужие данные. Добавлена проверка владения
  (`assertOwnedGoalAndStage`, `assertOwnedAccount`).
- CORS был открыт на `*`; сужен до `TELEGRAM_WEBAPP_URL` в проде.

**Функциональные пробелы (фича в API, но без UI — нерабочая для реального пользователя):**
- Не было формы добавления дохода/расхода — дашборд финансов всегда показывал 0.
- Не было UI создания/активации привычек — раздел "Привычки" был нефункционален.
- Не было способа удалить транзакцию, отредактировать/удалить долг или цель накоплений.
- Quick-add задач без даты не попадали на главный экран "Сегодня" (там фильтровались только
  задачи с явной датой) — основной сценарий "быстро накидал дел" был сломан.

**Данные/логика:**
- Весь код определения "сегодня" (вес, еда, задачи) использовал часовой пояс СЕРВЕРА, а не
  `User.timezone`. Создан `utils/userTime.ts`, подключён для веса/еды/времени middleware'ом
  `req.userTimezone`. Cron-расписание по-прежнему триггерится в фиксированное время сервера —
  это известное ограничение, требующее per-user планировщика (не исправлено).
- Streak привычки считался от даты залогированного события, а не от самой свежей записи —

## Шестнадцатый раунд: приложение на телефон

Папка `mobile/` — то же приложение без Telegram и без сервера. Все записи лежат в памяти самого телефона (IndexedDB). Логика серверной части (`backend/src`) не копировалась: при сборке подменяется только «инфраструктура» (база, маршрутизатор, настройки), поэтому задачи, цели, финансы, дневник и разбор записей работают тем же кодом. Размер: около 142 КБ в сжатом виде (скрипт и стили).

### Как получить файл .apk
1. Создай на github.com пустой репозиторий и загрузи в него содержимое архива проекта.
2. Открой вкладку Actions → «Сборка Android» → Run workflow (запускается и сама при каждом обновлении). Через 5–10 минут на странице запуска в разделе Artifacts будет `navigator-apk`. Внутри `app-debug.apk`.
3. Скачай файл на телефон и открой; Android попросит разрешить установку из этого источника.

Альтернатива без .apk: `cd mobile && npm install && npm run build`, папку `dist/` выложить на любой хостинг с HTTPS, в Chrome на телефоне выбрать «Установить приложение».

### Что есть в Android-версии
- Системные уведомления о напоминаниях планируются заранее и приходят при закрытом приложении (плагин local-notifications; повторяющиеся планируются на 6 ближайших раз и пересоздаются при каждом открытии).
- Копия данных уходит через системное меню «Поделиться» (там Google Диск). Раз в неделю на экране «Сегодня» появляется напоминание про копию.
- Блокировка входа через системный запрос отпечатка или лица.
- Значок приложения и нужные права добавляются скриптом `mobile/tools/android-prepare.cjs`.

### Что проверено, а что нет
Проверено (headless Chromium, реальный IndexedDB): запуск и знакомство; все разделы; запись в дневник → предложения → применение (с подменённым ответом AI); задачи, цели, привычки, вес, питание, траты, календарь, напоминания, идеи, память; сохранение после перезагрузки; работа без сети; выгрузка и восстановление; планирование уведомлений, копия и биометрия — **только против имитации плагинов**.

**Не проверено** (в этой среде нет Android SDK и доступа к Google): сама сборка .apk, установка и работа на настоящем телефоне, настоящие плагины уведомлений, «Поделиться» и биометрии (версия плагина биометрии подобрана по памяти и может потребовать правки в `mobile/package.json`). При первой сборке возможны ошибки, их нужно прислать текстом.

Цели и привычки в корзину не попадают (они удаляются вместе с этапами и историей), перед их удалением остаётся предупреждение. Корзина в файл копии не входит и очищается при «Удалить все данные».
- **Отчёт о проблеме** (Настройки): журнал последних сбоев; отчёт показывается целиком до отправки и не содержит текста записей.
- Перепроверка на ошибки (последний проход): исправлен сдвиг повтора «каждый месяц» с 31 числа; исправлена потеря записей корзины при параллельных удалениях (мьютекс); напоминания Android теперь пересоздаются после возврата из корзины и после «Удалить все данные»; везде «AI» заменено на «ИИ»; шифрование копии даёт понятную ошибку, если браузер без защищённого контекста. Добавлены проверки audit-ui, concurrency, contrast. Известное ограничение: повтор «каждый месяц» после 28 февраля остаётся на 28 числе.
- Быстрая настройка: на главном экране плашка (вставить ключ Gemini, включить напоминания и вечерний вопрос), пропадает, когда всё настроено или по «Позже». Кнопки-ссылки «Сохранить копию» исправлены на кнопки в стиле приложения.
- ИИ: Claude (ключ API Anthropic) теперь главный провайдер; Gemini и Groq — бесплатная замена и запасной вариант на случай отказа Claude. Модели: claude-haiku-5-5 (частые вызовы), claude-sonnet-5-5 (проверка). Подписка приложения Claude не даёт ключ API.
- ИИ-сервисы: можно подключить несколько ключей сразу (Claude, ChatGPT, Gemini, DeepSeek, Groq); в «Настройках» выбирается главный, остальные работают как запасные в порядке очереди. Модели ChatGPT (gpt-4o-mini) и DeepSeek (deepseek-chat) заданы в shim/env.ts. В capacitor.config.json включён CapacitorHttp, чтобы запросы к ИИ шли мимо ограничений браузера (CORS); на телефоне не проверено.
- Очередь ИИ (shim/aiRouter.ts): Claude, ChatGPT, Gemini, DeepSeek, Groq плюс любые сервисы формата OpenAI (шаблоны: OpenRouter free, Mistral, NVIDIA NIM, Cohere, Cloudflare Workers AI; или свой адрес; убраны Grok, Cerebras, Hugging Face и GitHub Models). Порядок меняется стрелками. При сбое сервис отдыхает: лимит 15 мин, нет денег 1 ч, ключ не принят или модель не найдена 6 ч, прочее 3 мин. Если на паузе все, всё равно пробуются по порядку. Названия моделей в шаблонах (shim/aiRouter.ts, PRESETS) сверены с открытыми источниками, но не проверены на живых серверах; в карточке есть «Проверить» и «Модель».
- Проверка сборки (v16): настройки ИИ читаются устойчиво к мусору; карточка приватности и плашка настройки учитывают сервисы из очереди; исправлена ошибка типа при сохранении ключей.
- Глубокая проверка (v17): длинное слово без пробелов больше не растягивает экран; двойное нажатие «Добавить» и «Записать» создаёт одну запись (одинаковые одновременные запросы на создание выполняются один раз); сервер отклоняет пустые записи из пробелов и слишком большие суммы и вес; запись дневника не длиннее 20 000 знаков; кнопки-фильтры задач переносятся, а не прячутся за краем; восстановление копии пропускает записи, которые уже есть (повторное восстановление того же файла ничего не удваивает; в итоге показывается «Уже были в приложении, пропущены»).
- Известные ограничения повторов: «каждый месяц» после короткого месяца остаётся на меньшем числе (31 января → 28 февраля → 28 марта…); ежедневное или еженедельное напоминание на время 03:00–03:59 в поясах с переходом на летнее время (например, Киев) после весеннего перехода сдвигается на 04:xx и остаётся там. Для остальных времён переходы проходят чисто.
- Обновление без потерь (v1.18.0, подробно в mobile/UPDATES.md): подпись одним постоянным ключом и растущий versionCode (иначе Android не ставит поверх), сборка публикует navigator.apk в Releases; в приложении «Версия и обновление» (проверка, скачивание с полосой, установка через свой плагин ApkInstaller), точки восстановления (перед обновлением и раз в сутки, откат одной кнопкой), версия данных с миграциями (shim/safety.ts), защита от более новых данных. Бесплатные ИИ-сервисы стоят первыми в очереди, платные в конце. Не проверено на живом телефоне и в реальном GitHub Actions: сборка с подписью, плагин ApkInstaller, установка поверх старой версии (Java-код проверен только компиляцией на заглушках).
- Не сделано: виджет на экран телефона (нужен нативный код на Kotlin; я не могу его собрать и проверить, а ошибка в нём сломала бы сборку всего .apk).

### Ограничения
- Данные только на телефоне. Автоматической копии на Диск нет: нужно нажимать кнопку (приложение напоминает раз в неделю).
- Android может отложить уведомления при строгой экономии заряда; в настройках телефона разреши приложению работать без ограничений.
- Ключи AI хранятся на телефоне. Без ключа дневник, задачи и учёт работают, но предложений и итогов нет.
- Это отладочная подпись (debug): подходит для установки себе, но не для публикации в Google Play.
- Версия для Telegram остаётся в репозитории; в её код внесено только исправление восстановления копии (см. выше). Перед каждым выпуском поднимайте `VERSION` в `mobile/public/sw.js`.

## Осознанно требует ваших дополнительных ключей (не Anthropic)

Три функции по своей природе не могут работать через Claude API — у Anthropic нет
embeddings и audio API. Код полностью готов, но неактивен без отдельных ключей:

- **Life Graph** (раздел 22) — ✅ полностью готово, работает без доп. ключей
  (выводится из существующих связей goalId/stageId в БД). Экран `/life-graph`.
- **Semantic Memory** (раздел 37) — код готов, но настоящий семантический поиск
  требует `VOYAGE_API_KEY` (Anthropic сама рекомендует Voyage AI для embeddings).
  Без ключа `/memory/search` работает в облегчённом режиме — поиск по словам.
- **Голосовой ввод** (раздел 44, Версия 2) — код готов (бот принимает voice-сообщения,
  распознаёт их и превращает в вес/еду/задачу), но требует `OPENAI_API_KEY` для
  Whisper API. Без ключа бот вежливо просит написать текстом.
- **Natural language через бота** (раздел 2) — теперь работает не только в Mini App,
  но и прямо в чате с ботом: «Вес 90.4», «Съел 250г курицы» и любой свободный текст
  автоматически превращаются в структурированные данные (с AI-классификацией интента,
  либо простой эвристикой без AI-ключа).
